# OpenClaw Pixel Agents 1.8.0 — Agent controls and easier setup

This release brings source-backed run history, live task controls, approval handling, conversation model selection and native scheduling to the office. Guided configuration and an editable agent roster make installation possible without source changes or rebuilding. The office also has a new pixel-art city background.

## Guided setup and your own agents

- Run `openclaw-pixel-agents configure` in an interactive terminal to prepare a new private configuration bundle for local OpenClaw or a remote collector.
- Keep the eight built-in agents, or enter 1–50 existing OpenClaw IDs and public display names. The wizard writes an editable `agents.json`; changing IDs/names later needs an office restart, not a build. An explicit roster replaces the defaults and remains the ingest/private-agent allowlist.
- Review the settings with secrets hidden before agreeing to save. The wizard refuses existing destinations, never starts services, contacts a Gateway or pairs a device, and does not edit an existing office configuration.
- `setup` remains an instructions-only command. `configure` creates files only after confirmation; neither command grants Gateway permissions.

See [guided configuration](https://github.com/SweetSophia/openclaw-pixel-agents/blob/main/docs/configuration.md#guided-configuration) and [custom rosters](https://github.com/SweetSophia/openclaw-pixel-agents/blob/main/docs/configuration.md#custom-agent-rosters). IDs must match OpenClaw exactly; the wizard does not create or discover OpenClaw agents. The local CLI's shell-free execution does not support Windows `.cmd`/`.bat` shims; native Windows execution is not established by Linux qualification.

## Run history and live controls

- Select a source-backed recorded run across Task, Conversation and Results, then explicitly return to **Live / latest task**. Historical selection is read-only; Usage does not invent per-run billing and approvals/model actions are suppressed.
- Choose follow-up or explicit conversation steering. Steering acts on direct work at native admission and can start a new turn if the conversation became idle first; it is not an exact-run interruption guarantee.
- Confirm **Stop** only for a freshly verified exact active run. A requested receipt confirms admission, not completion; an uncertain outcome requires authoritative refresh, not automatic replay.
- Inspect and confirm an eligible live conversation's model preference, or explicitly reset it to the configured default. Known-busy or activity-unknown conversations cannot change models. Work racing the idle check may still switch models or restart under native behavior; a preference acknowledgement is not execution proof.

These writes use `CONTROL_SEND_ENABLED=true`, the ordinary device's separately approved `operator.read`/`operator.write` grant, and supported native methods. Upgrading alone grants no new authority. Model changes do not alter global defaults or auth profiles, and reject unexpectedly administrator-granted connections. See [live controls](https://github.com/SweetSophia/openclaw-pixel-agents/blob/main/docs/task-access-setup.md#live-follow-ups-steering-and-stop) and [model selection](https://github.com/SweetSophia/openclaw-pixel-agents/blob/main/docs/task-access-setup.md#conversation-model-selection).

## Private approval handling

Approvals shows bounded native requests visible to the selected live conversation audience. Inspect an exact request, review its operation and target, then choose **Allow once** or **Deny**. Native reviewer policy and first-answer truth remain authoritative; visibility is not proof of attribution to a particular recorded run.

Approval review is independently default-off: it needs `CONTROL_APPROVALS_ENABLED=true`, an explicitly approved `operator.approvals` grant and compatible native methods/reviewer binding. Existing grants are never silently upgraded. Unknown decisions are reconciled by reads, not replayed. See [approval setup and recovery](https://github.com/SweetSophia/openclaw-pixel-agents/blob/main/docs/task-access-setup.md#private-approval-handling).

## Native agent scheduling

- Browse native agent schedules without selecting a conversation. Compatible jobs support interval or five-field cron/IANA-timezone definitions; native timing and DST semantics remain authoritative.
- Create **disabled** schedules first, then inspect and separately confirm Enable. Edits, Enable and Pause are fenced to the reviewed native configuration revision. Pause affects future scheduling, not an already running task.
- Keep creation recovery metadata in a private durable journal before first dispatch. Lost replies remain uncertain across restart; bounded explicit reconciliation never automatically repeats an add/upsert that could overwrite another operator's change.

Management is independently default-off through `CONTROL_SCHEDULES_MANAGE_ENABLED=false`. Enabling it requires deliberate pairing of a **separate** `operator.read`/`operator.admin` scheduling device and separate temporary bootstrap credentials. The four-method application allowlist is not a cryptographic restriction of that broader admin grant; protect and revoke it independently. Do not broaden the ordinary Task/Conversation device. New schedules have no scheduler announcements or failure alerts, but this does not sandbox an agent's tools.

Pixel Agents does not run a second scheduler. There is no Delete, Run Now, one-shot date, arbitrary delivery or generic RPC control. Shutting down the office or removing an agent from its roster does not pause native jobs. See [scheduling setup, storage and recovery](https://github.com/SweetSophia/openclaw-pixel-agents/blob/main/docs/schedules.md).

## Reliability and privacy

The release includes source hardening for monotonic confirmation expiry, stale/late-response fencing, exact millisecond interval round trips, post-confirmation focus, revision-consistent recovery scans, atomic journal replacement reads and bounded shutdown after storage errors. Proven pre-dispatch rejection is distinguished from an uncertain native mutation; uncertainty never becomes permission to replay.

Private-control API responses, drafts and credentials are not added to the public office socket or browser storage. This protects that private-control channel, not every source of transcript text in the dashboard. The office key is shared trusted-operator access, not per-user RBAC or whole-dashboard authentication.

**The existing public activity ticker is separate:** while local CLI polling is active, it can broadcast user and assistant transcript excerpts (up to 150 characters per message) to dashboard clients without `PIXEL_CONTROL_TOKEN`. Sensitive offices must restrict access to the **entire dashboard, including Socket.IO**, through network access controls or an authenticated reverse proxy. CORS alone is not authentication. See [private access and the public ticker](https://github.com/SweetSophia/openclaw-pixel-agents/blob/main/docs/configuration.md#private-access).

Missing optional Gateway capabilities or grants remain unavailable rather than being emulated or bypassed. Synthetic package, browser and signed-Gateway tests are not evidence of live pairing or task execution.

## Upgrade safely

The commands below apply to the published 1.8.0 artifact. A source merge, version bump or preparation PR does not publish it; check the GitHub release and npm version before upgrading:

```sh
npm view openclaw-pixel-agents@1.8.0 version
npm install --global openclaw-pixel-agents@1.8.0
openclaw-pixel-agents --version
openclaw-pixel-agents setup
```

Before changing a running installation, stop it and preserve a private backup of its configuration and entire **`DATA_DIR`**, including layouts, appearances, `control/`, any existing `control-schedules/`, and an external roster file. Retain private permissions and keep backups out of Git. Restart using the **same environment file, keys and data path**. The raw npm launcher still defaults to `~/.openclaw-pixel-agents`; direct source startup and Docker have different defaults. Use an explicit stable absolute `DATA_DIR` for services.

Do not rerun `configure` as an in-place migration: it creates a separate bundle and suggests a different data path. If adopting it for an existing office, deliberately select the existing `DATA_DIR` and transfer reviewed settings without rotating credentials or losing state. Without `AGENT_ROSTER_PATH`, the existing eight-agent defaults remain. Name changes preserve ID-keyed settings; ID changes select a different identity. Include every collector-submitted ID in a custom roster or the snapshot is rejected.

No new permission is enabled by the upgrade. Existing send opt-in remains meaningful for newly available controls, so review who holds the office key before use. Approvals and scheduling management each remain separately default-off. Keep uncertain schedule journal records: never reset/delete them or restart to make a native mutation retryable. Consult each control's recovery guide before rollback or retry; Stop, approvals and model replay guards are process/tab-memory protections, not durable cross-restart deduplication.

The supported Node.js range remains **`^22.22.2 || ^24.15.0 || >=26.0.0`**. Source users must build before starting; Docker users must rebuild the image while retaining their data volume and private configuration. Workspace editing/uploads, external-channel delivery and per-user accounts are not part of 1.8.0.
